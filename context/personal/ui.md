# UI Preferences

画面を作るときに読む。`generic/frontend.md`（一般的な既定）に対する、オーナー固有の好み。

## 全体方針

- `MUST` 視覚構成をシンプルに保つ。ここでのシンプルとは、情報量や個性を減らすことではなく、構造と意図が明快であること。
- `MUST` UIを無味乾燥にしない。操作を邪魔しない範囲で遊び心を持たせる。
- `MAY` 次の2系統のどちらも採用する。どちらも正当な好みであり、片方を常設の既定にしない。
  1. Windows 98などを想起させる、古く、四角く、境界の明確なUI。
  2. 最近のWebのような、角の丸い矩形を使うスタイリッシュなUI。
- `SHOULD` 系統は、用途、雰囲気、対象端末、その時点で提示された参考デザインに合わせて選ぶ。
- `DO NOT` 2系統を根拠なく混ぜる。意図的に混ぜるなら、一貫した接続ルールを決める。

### 古いUI系統のとき

- `MUST` オーナーがその時点で挙げた参考例を優先する。「レトロ風」と推測して固定しない。
- `SHOULD` 四角い部品、明確な枠線、階層が読み取れる面構成。アニメーションは基本的に使わない。状態変化は即時かつ明確に。
- `DO NOT` 現代的UI向けの配色、透明感、角丸、カード表現を自動的に持ち込む。
- `MAY` 見た目は当時に寄せつつ、可読性・入力支援・エラー回復といった現代的なUXの改善は保つ。

### 現代的UI系統のとき

- `SHOULD` 角の丸い矩形を基本の形にできる。
- `MAY` 薄い影、境界線、フラット表現、半透明、ぼかし、カードを使う。いずれも状況依存で、全要素への一律適用ではない。
- `AVOID` カードの過剰な入れ子、境界が曖昧になるほどの透明・ぼかし。
- `SHOULD` 立体感の表現方式を画面内で揃え、階層と操作可能性が読めるようにする。

## 色

- `SHOULD` 高彩度を避け、やや落ち着いた色を使う。
- `PREFER` オレンジ系、黄緑系、水色系。プロジェクトごとに使う色と役割を決め、3系統すべてを同時に使う必要はない。
- `SHOULD` ライトテーマは白基調に、ある程度明度の高い色。ダークテーマは黒基調に、ライトより少し明度を落とした色。
- `MAY` 色付きの面や部品に不透明度80%程度を使う。暫定的な嗜好であり、可読性・背景との干渉・コントラストで調整する。
- `MUST` 文字と重要情報の読みやすさを配色より優先する。

## 情報密度と画面構成

- `MAY` 日本の業務ソフトのように一画面へ多く載せる構成と、必要十分に絞る構成のどちらも採る。
- `MUST` 情報量の少なさ自体をモダンさ、多さ自体を使いにくさと見なさない。
- `SHOULD` 頻度、比較の必要性、一覧性、画面サイズ、習熟度から密度を決める。
- `MUST` 不要な設定項目や内部都合の選択肢まで出して、見かけ上の高密度を作らない。
- `SHOULD` 高密度でも、整列・区切り・見出し・余白・色の役割を一貫させ、目で走査できるようにする。
- `SHOULD` 基本項目と詳細項目を分離し、主要操作を詳細設定へ埋めない。
- `AVOID` 内容が少ないのにカードやページを大量に分割すること。役割の違う大量の情報を、区切りなく一本の長い画面に並べること。

## ナビゲーション

- `PREFER` 左サイドバーと上部タブ／メニュー。用途とアプリの雰囲気で使い分ける。
- `SHOULD` PCでは操作やコマンドを上部タブ／メニューに置ける。項目の選択やウィンドウ内の機能切り替えにはサイドバーを使える。
- `SHOULD` スマートフォンではサイドバー的な分類を中心にできる。狭い画面では常時表示せずドロワー等に収めてよい。
- `MUST` 現在位置と選択中の項目を明確にする。
- `MUST` PCの高密度画面を、そのまま縮小してスマートフォンへ押し込まない。端末ごとに優先順位・並び・表示方法・ナビゲーションを調整する。
- `AVOID` 同じ階層への移動手段を、複数箇所へ無秩序に重複させること。

## 操作・フォーム・状態

- `MUST` 重要な操作には、意味が伝わる文字付きボタンを使う。アイコンだけで重要操作を表さない。
- `MAY` 補助的または十分に一般的な操作にはアイコンを使う。曖昧なら文字かツールチップを添える。
- `SHOULD` 主要操作と補助操作の視覚的な優先度を分ける。
- `SHOULD` 表示、並び順、軽微な好みなど、影響が小さく結果がすぐ分かる変更は即時反映してよい。取り消しか既定値への復帰手段があるとよい。
- `SHOULD` 複数項目の整合が要る設定、外部に影響する変更、処理コストがある変更、重大な変更は、明示的な適用・保存にする。
- `MUST` 保存前の変更・保存中・保存済み・保存失敗を混同させない。
- `AVOID` 一つの設定画面内で、即時反映と保存式を説明なく混在させること。
- `SHOULD` アニメーションは必要最低限かつ短く、状態変化が認識できる程度に。現代的UIでは小さな反応を遊び心に使える。
- `MUST` アニメーションで、操作完了・待機・失敗の判定を遅らせたり曖昧にしたりしない。

## 空状態と成功通知

- `MUST` データが無いことは簡潔に示す。
- `AVOID` 不要なイラスト、長い説明、過剰な誘導、実データと誤認し得るサンプルで空白を埋めること。
- `MAY` 開始に不可欠な操作が一つだけ明確にあるなら、簡潔な操作手段を添える。
- `SHOULD` 成功通知は失敗通知より目立たせない。後から確認が要る処理は、履歴か対象の状態に反映する。

## 遊び心

- `SHOULD` 文言、小さな反応、アイコン、イラスト、隠し要素で味気なさを避ける。
- `MUST` 遊び心で主要操作、状態、エラー、危険性を分かりにくくしない。
- `SHOULD` 隠し要素は、発見しなくても通常利用に支障がないものにする。
- `AVOID` 重要な説明を冗談だけで済ませること。失敗時に利用者をからかう表現。

## 未定（プロジェクトごとに決める）

書体、文字サイズ体系、アイコンセット、角丸の半径、余白スケール、影の強度、正式なアクセシビリティ適合水準、対応端末と最小画面幅、個々の色コードと配色比率、ブランド表現やイラストの画風。指定がなければ一般的なUX原則を暫定適用し、「暫定」と明記する。
