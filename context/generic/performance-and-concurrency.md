# Performance and Concurrency

速度・資源・並行処理を扱うときに読む。

## 性能

- `MUST` 性能を主張する前に、対象環境、負荷、利用者から見た目標、測定方法を定義する。
- `DO NOT` 測定が可能な場面で、勘だけで最適化する。
- `SHOULD` 代表的な基準値を測り、意味のある要因を一つ変え、再現可能な入力で比較する。
- `MUST` 最適化で正しさ、データ安全性、セキュリティを損なわない。速く間違うのは改善ではない。
- `AVOID` 証拠がその複雑さを正当化しない限り、キャッシュ、並行化、バッチ、ネイティブ化、分散、専用基盤を導入すること。
- `MUST` それらを導入するなら、無効化、メモリ上限、詰まったときの挙動、失敗時の挙動を定義する。
- `SHOULD` 待機時の資源消費を、稼働時とは別に評価する。
- `SHOULD` 実際の対象ハードウェアと負荷に対して評価する。汎用の性能予算を当てはめない。

## 並行処理と状態

- `MUST` 並行化の前に、共有される可変状態、所有者、順序の要求、不可分にすべき範囲を特定する。
- `SHOULD` 逐次実行で要件を満たせるなら並行化しない。並行性は障害と理解の費用を増やす。
- `MUST` 重複要求、再試行、取り消し、タイムアウト、部分完了、プロセス中断時の挙動を定義する。
- `SHOULD` 外部から再試行される操作は冪等にするか、リスクに見合う重複排除・トランザクション機構を使う。
- `MUST` 更新の消失と不正な交錯を、直列化、トランザクション、ロック、楽観的並行制御、不変性などの正当化できる手段で防ぐ。
- `DO NOT` 適当な待ち時間を同期の手段に使う。
- `MUST` キュー、ワーカー、メモリ、再試行に上限を設け、過負荷時の挙動を定義する。
- `MUST` 保留、実行中、成功、失敗、取り消し、不明を区別できる状態を保つ（区別が意味を持つ場合）。
