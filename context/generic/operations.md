# Operations

ログ、リリース、Git操作のときに読む。

## ログと診断

- `MUST` 重要な失敗を、デバッガで再現せずに診断できるようにする。
- `SHOULD` 運用者が答えを知りたい問いに応じて、ログ、メトリクス、トレース、監査記録、ヘルスを選ぶ。全部が要るとは限らない。
- `MUST` 境界をまたぐ因果を、リクエストID等の識別子で保つ。
- `MUST` エラーは操作、結果、安全な文脈と共に記録する。秘密を除き、個人データを最小化する。
- `SHOULD` 機械やLLMが解析する診断は、安定したイベント名と構造化フィールドにする。
- `MUST` 想定内の利用者エラー、一時的な外部障害、機能低下、内部の欠陥を区別する。
- `SHOULD` ログレベルと詳細度を、コード変更なしに変えられるようにする。
- `DO NOT` プロセスが動いていることだけを根拠に正常と報告する。

## リリース

- `MUST` 成果物、元のリビジョン、設定の前提、データ互換性、巻き戻し・復旧経路を定義する。
- `MUST` リスクに応じて、テスト、移行、パッケージング、運用確認をリリース前に済ませる。
- `SHOULD` 配布物を追跡・再現できる形にする。
- `MUST` 部分的な入れ替えが起こり得るなら、混在バージョンでも安全な順序でアプリとデータの変更を並べる。
- `MUST` 中止条件を決め、巻き戻しまたは前進復旧が実際に効くことを確認する。存在の主張だけでは足りない。
- `DO NOT` デプロイコマンドの成功を、製品が使える証拠と見なす。
- `MAY` 影響の小さい個人用ツールでは、追跡可能性と安全な更新を保った上で、手順を簡素にする。

## Gitと変更管理

- `MUST` 編集前にリポジトリの状態を確認し、無関係な変更を保全する。
- `MUST` 変更をレビュー可能な範囲に保つ。無関係な箇所を整形・改名・書き換えしない。
- `SHOULD` コミットは意図と影響を書く。環境かオーナーが求めない限りコミットしない。
- `DO NOT` 共有履歴の書き換え、作業の破棄、force push、破壊的な整理を、明示的な許可なく行う。
- `MUST` 移行、生成物、ロックファイル、ドキュメントが変更の一部なら含める。一時生成物と秘密は除く。
