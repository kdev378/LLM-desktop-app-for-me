# 07 — 保存形式・移行・バックアップ

## 方針

データベースを使わない。理由:

- ネイティブモジュール（better-sqlite3 等）は Electron の ABI と Node の ABI で
  別々のビルドが要り、3OS × 2ランタイムの組み合わせが増える。個人用ツールの規模に見合わない。
- 手で読める。壊れたときに中身を見て判断できる。
- 会話1つは大きくても数百KB。1000会話でも数百MB。線形走査で足りる。

**この判断が破綻する条件**を先に決めておく。
会話が5000件を超える、または一覧表示が体感で1秒を超えたら、SQLiteへの移行を検討する
（`schemaVersion` を上げ、JSONからの一方向移行を書く）。それまで索引を作らない。

## ディレクトリ

```
<root>/
  config.json
  credentials.json                  # 0600
  conversations/
    <ulid>.json                     # 会話1つ
    <ulid>.files/                   # その会話の添付
  projects/
    <ulid>/
      project.json
      files/                        # 資料
  backups/
    <runId>/
      journal.json
      001-main.ts
  index/
    <indexId>/
      meta.json                     # 埋め込みモデルと次元。合わないものは混ぜない
      chunks.jsonl
      vectors.bin                   # Float32Array。DBを使わない（14-memory.md）
  worktrees/
    <runId>/                        # git worktree。実行が終わっても消さない
  server.json                       # ハーネスAPIのトークン。0600
  logs/
    akari-2026-09-05.log
  akari.lock
```

`index/` と `worktrees/` は**再生成できる**か、**git に残っている**。
`conversations/` `projects/` `backups/` は再生成できない。バックアップの優先度が違う。

会話ファイルには、生のメッセージに加えて圧縮の記録（`compactions`）が入る。
**圧縮は生のメッセージを置き換えない。** 何を送るかが変わるだけで、
保存されているものは減らない（`16-context.md`）。
そのため会話ファイルは圧縮しても小さくならない。これは意図した挙動。

ファイル名に ULID を使う。時刻順に並び、衝突せず、ファイルシステムに安全な文字だけを含む。

## 書き込みの規則

すべての保存は次の手順で行う。途中でプロセスが落ちても、旧版か新版のどちらかが残る。

1. `<name>.tmp-<pid>-<rand>` へ書く
2. `fsync` する
3. `rename` で本来の名前へ置き換える（同一ファイルシステム内なので原子的）
4. 親ディレクトリを `fsync` する（POSIX のみ。Windows では省略）

同一ファイルへの書き込みは、プロセス内でパス単位のキューにより直列化する。

## 多重起動

`akari.lock` に PID と起動時刻を書く。

- 既存のロックがあり、その PID が生きているなら、既存ウィンドウを前面に出して終了する。
- PID が死んでいるなら、ロックを奪って起動する。
- CLI はロックを取らない。デスクトップと同時に動いてよい。
  同じ会話を同時に編集した場合、**後の書き込みが勝つ**。これは既知の制限として文書化する
  （個人用の1人利用を前提とするため、複雑な排他を導入しない）。

## スキーマとバージョン

各ファイルの先頭に `schemaVersion`（整数）を持つ。

| 読んだ値 | 挙動 |
|---|---|
| 現行と同じ | そのまま使う |
| 現行より小さい | 移行を適用してから使う。書き戻すのは、利用者がそのデータを実際に変更したときだけ |
| 現行より大きい | **読み取り専用**として開き、警告を出す。書き込みは禁止 |
| 欠落 | `1` とみなす |

## 移行の規則

- 移行は「読んだときに1件ずつ」行う。起動時に全ファイルを一括変換しない
  （中断されたときに半分だけ変わった状態を作らないため）。
- 破壊的な移行（項目の削除、意味の変更）の前に、`<root>/backups/migration-<version>-<date>/`
  へ対象ファイルをコピーする。コピーの完了を確認してから変換する。
- 移行は冪等にする。同じファイルへ2回適用しても同じ結果になること。
- **解釈できないデータを黙って捨てない。** 未知の項目は保持したまま書き戻す。
  どうしても保持できない場合は、`<root>/quarantine/` へ元のファイルを退避し、
  何を退避したかを起動時に表示する。

## バックアップ

| 対象 | 方式 | 保持 |
|---|---|---|
| エージェントのファイル変更 | 変更前のコピー（`05-agent.md`） | 30日 / 1GB |
| 移行前のデータ | ディレクトリごとコピー | 手動で消すまで |
| 会話・プロジェクト全体 | 利用者が「書き出し」を実行したとき、zip 1つ | 保存先は利用者が選ぶ |

「書き出し」は `config.json`（鍵を除く）、`conversations/`、`projects/` を含む zip を作る。
`credentials.json` は**含めない**。含めないことを画面に書く。

「読み込み」は、既存を消さずに追加する。ID が衝突した場合は新しい ID を振り直す。
上書きの選択肢は v1 では出さない（取り返しがつかないため）。

## 削除

- 会話・プロジェクトの削除は、`<root>/trash/` へ移動する。即座には消さない。
- ゴミ箱は30日で自動削除する。設定画面から手動で空にできる。
- 削除前に「N件のメッセージ / M件の会話が入っています」を示す。
