# 11 — 実装順序と検証計画

## 原則

不確実性の高いところから潰す。各段階の終わりに、**オーナーが自分で確かめられる操作**が
1つ増えている状態にする。「基盤だけできたが何も動かない」段階を作らない。

## 順序の考え方

当初はデスクトップのChatを先に作る予定だったが、**エージェント先行**に変えた。

理由: この製品の価値は「LLMに手を動かさせる」ところにあり、
外部のマルチエージェントツールから使えるようになるのが最短の実用化だから。
デスクトップの画面は、動く中身ができてから被せるほうが手戻りが少ない。

```
P0 接続             [完了・実機未確認]
P1 エージェント中核  [完了]
P2 文脈の圧縮と recall [実装済み / 実モデルでの確認待ち]
P3 ハーネスAPI       ← 外部ツールから使えるようになる
P3+ コマンドの閉じ込め ← 外部から full で無人実行させる前に
P4 MCP
P5 記憶（ベクトル索引）
P6 Web
P7 デスクトップ Chat
P8 Work と Code の画面
P9 仕上げと配布
```

## P3+ — コマンドの閉じ込め（サンドボックス）【実装済み。Linux で確認、macOS は確認待ち】（2026-10-28）

**なぜ要るか**: 作業フォルダの境界と秘密ファイルの読み取り禁止は、ファイルの道具にしか
効かない。`run_command` は利用者の権限で動く本物のシェルなので、`cat .env` や
作業フォルダの外への書き込みができる。`full` ではそれが自動で通る（2026-10-27 に確認）。
P3 で外部のエージェントが `full` のまま無人で走らせられるようになると、ここが効いてくる。
それまでは文書での注意で運用する（`commands.md`「`full` でも通らないもの」）。

**方針**: コマンドを OS の仕組みで閉じ込める。ツールは使えるまま、書き込みと秘密を塞ぐ。

| 対象 | 既定 |
|---|---|
| システムとツールの場所（`/usr` `/opt` `~/.cargo` `~/.nvm` など）の読み取り | 許す |
| 作業フォルダと一時フォルダへの書き込み | 許す |
| それ以外への書き込み | 塞ぐ |
| 秘密の場所の読み取り（`~/.ssh` `~/.aws` `~/.gnupg` `~/.config/akari`、作業フォルダ内の `.env` 等） | 塞ぐ |
| ネットワーク | 許す（依存の取得に要る）。塞ぐ設定を別に持つ |

- **ホームを丸ごと塞がない。** ツールがホームの中に入っていることが多く（`~/.cargo` など）、
  丸ごと塞ぐとコンパイラが使えなくなる。秘密の場所を名指しで塞ぐ。
- chroot は使わない。管理者権限が要り、システムのツールが見えなくなり、守りの仕組みでもない。
- 仕組み: macOS は Seatbelt（`sandbox-exec`）、Linux は bubblewrap。
  Windows は未定。**閉じ込められない環境では、閉じ込めていないことを実行開始時に表示する。**
  閉じ込めているふりをしない。
- 未確認: `sandbox-exec` は Apple が非推奨にしているが、現行の macOS で動くか。
  bubblewrap が入っていない Linux での扱い。

検証すること:
- [x] `full` でも、コマンドから `cat .env` / `cat ~/.ssh/id_rsa` / Akari の設定が読めない（Linux・bubblewrap、自動テスト）
- [x] コマンドから作業フォルダの外へ書けない（`echo x > ../a`、`touch ~/a`）（同上）
- [x] 作業フォルダ・一時フォルダ・道具のキャッシュには書け、`node` `git` が動く（同上）
- [x] ホームに入ったツール（`~/.cargo/bin` の実行ファイル）が使える（同上）
- [x] 閉じ込められない環境では、その旨が実行開始時に出る。`required` ならコマンドを実行しない
- [x] ネットワークは既定で使え、`network: false` で塞がる（同上）
- [x] worktree の中の `git commit` が通る（元の `.git` には書ける）（同上）
- [x] モデルが `.env` の読み取りを求め、利用者が許すとその実行の間だけ読める（オーナーの要望。どの権限でも毎回聞く）
- [x] 閉じ込められない環境では、HTTP からの `full` を断る
- [x] 別の Linux（Muse の VM、bubblewrap 0.9.0）でも `pnpm test:sandbox` と手での確認が通った（2026-10-29）
- [ ] **macOS（Seatbelt）で同じ確認**（`testing.md` 11-9。規則の組み立ては自動テストで確かめたが、動かしていない。オーナーが macOS の VM で試す予定）

## テストの方針

`generic/quality.md` に従い、リスクで選ぶ。全部にテストを書かない。

| 対象 | 種別 | 理由 |
|---|---|---|
| パス境界の検査 | 単体（重点） | ここが破れると作業フォルダの外が壊れる |
| SSRF の検査 | 単体（重点） | ここが破れると内部ネットワークが読まれる |
| ハーネスAPIの認証とCORS | 結合（重点） | ここが破れると外からコマンドを実行される |
| 変更記録と `undo` | 単体 + 結合 | 復旧可能性の根拠そのもの |
| SSE の解釈、`tool_calls` の連結 | 単体（記録した実応答を使う） | サーバごとの差異が入る |
| イベントの再送と `gap` | 結合 | チャットボットが落ちても経過を失わないこと |
| `prompted` モードの解釈 | 単体 | 曖昧な入力を弾くことが要件 |
| 承認モードの表 | 単体 | 表と実装がずれると危険 |
| 設定の検証と移行 | 単体 | 黙って既定へ落とさないこと |
| ターン境界を壊さない圧縮 | 単体（重点） | 壊すと API が 400 を返し、実行が止まる |
| 圧縮しても生が消えないこと | 結合 | 「消さない」がこの機能の前提 |
| 埋め込みの次元・モデル不一致 | 単体 | 混ぜると無意味な結果が出る |
| 索引の検索速度 | 実測 | 方針の前提そのもの |
| Chat の送受信 | 結合（モックサーバ） | — |
| 実サーバとの疎通 | 手動（各段階の確かめ方） | 自動化の費用が見合わない |
| 画面の見た目・操作感 | 手動 | 同上 |

模擬サーバ `tools/mock-llm-server.mjs` に、埋め込みとツール呼び出しの応答を足していく。
