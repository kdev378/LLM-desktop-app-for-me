# 11 — 実装順序と検証計画

## 原則

不確実性の高いところから潰す。各段階の終わりに、**オーナーが自分で確かめられる操作**が
1つ増えている状態にする。「基盤だけできたが何も動かない」段階を作らない。

## P0 — 接続の確認（最も不確実）

ローカルLLMサーバごとの差異が最大の未知。ここが崩れると全部の前提が変わるので最初にやる。

作るもの:
- pnpm workspace、TypeScript strict、lint/format の設定
- `@akari/core` の `config` と `provider`
- CLI の `models` / `chat` / `doctor` のみ

確かめ方:
```sh
akari config endpoints add --name local --url http://localhost:11434/v1
akari models                 # → モデル一覧が出る
akari chat                   # → 対話でき、応答が流れて出る
akari doctor                 # → 機能判定の結果が出る
```

検証すること:
- [x] ツール呼び出しのストリーム断片が連結される（模擬サーバ）
- [x] `stream_options` 非対応時のフォールバックが効く（模擬サーバ）
- [x] サーバへ到達できないとき `unreachable` に分類される（実測）
- [x] トークン受信後の切断で、受信済みを残し再試行しない（模擬サーバ）
- [x] `stream: true` を無視して一括JSONを返すサーバでも本文が出る（模擬サーバ）
- [ ] **Ollama / llama.cpp / LM Studio / vLLM の4種の実機で `/models` と生成が動く（未実施）**
- [ ] **実機でのツール呼び出しストリーム形式（未実施。`02-provider.md` の未解決の仮定は残ったまま）**
- [ ] `Ctrl+C` で対話モードの生成が止まる（対話端末が要るため自動テスト未実施）

模擬サーバ `tools/mock-llm-server.mjs` は本物の代わりにならない。
実機での確認が済むまで、上の未チェック項目は「動く見込み」であって「動く」ではない。

**この段階で仮定が外れたら、`02-provider.md` を先に更新する。**

## P1 — デスクトップの Chat

作るもの:
- Electron の骨格（メイン / preload / renderer）とセキュリティ設定
- `store`（会話の保存・読み込み・一覧）
- Chat 画面：一覧、送信、ストリーム表示、停止、Markdown、コードハイライト
- 設定画面：接続先の追加・切替・機能判定

確かめ方: アプリを起動 → 接続先を登録 → 会話 → 再起動しても残っている → 停止できる

検証すること:
- [ ] 生成中にアプリを強制終了しても、それまでの応答が残る
- [ ] renderer から `require` や外部URLへ到達できない
- [ ] モデル出力に `<script>` を含めても実行されない
- [ ] 3OSで起動し、日本語が正しく表示・入力できる（IME変換中の Enter で誤送信しない）

## P2 — 枝分かれとプロジェクト

作るもの:
- メッセージの木構造、編集・再生成・枝の切替
- `Project` のデータと画面、資料の添付、設定の継承
- 検索、ゴミ箱、書き出し / 読み込み

確かめ方: 過去の発言を編集 → 枝が増える → `< 1/2 >` で行き来できる → 消えていない

検証すること:
- [ ] 100件のメッセージを持つ会話で、枝を切り替えても内容が壊れない
- [ ] 書き出した zip を読み込むと、会話が重複せず追加される
- [ ] `credentials.json` が zip に入っていない

## P3 — エージェントエンジン（core）+ CLI

最も事故が起きやすい部分。**CLIで先に作る**。画面より検証が速く、境界の穴が見つけやすい。

作るもの:
- `tools`（8種）とパス境界の検査
- `agent`（実行ループ、承認、上限、中断）
- 変更記録とバックアップ、`undo`
- CLI の `run` / `diff` / `undo` / `runs` / `--json`

確かめ方:
```sh
cd /tmp/sandbox && akari "hello.txt に挨拶を書いて"
akari diff        # → 差分が出る
akari undo        # → 元に戻る
```

検証すること（**ここは重点的にテストを書く**）:
- [ ] `../` を含むパス、絶対パス、シンボリックリンク経由で workspace の外へ出られない
- [ ] workspace の外へのリンクを張ったディレクトリ経由でも出られない
- [ ] `edit_file` で `oldText` が複数一致したら実行されない
- [ ] `deniedCommands` が `full` モードでも効く
- [ ] コマンドが子プロセスを作った場合、タイムアウトでプロセスグループごと消える
- [ ] 実行後に手でファイルを変えた状態で `undo` すると、そのファイルは飛ばされ報告される
- [ ] 非対話（パイプ）で承認が要る操作が自動拒否され、終了コード 3 になる
- [ ] 同じツール・同じ引数を3回繰り返したら停止する
- [ ] 中断したとき、実行中のコマンドが残らない

## P4 — Work（プロジェクト + エージェント実行UI）

作るもの:
- 実行タイムライン、承認ダイアログ、差分プレビュー
- 「この実行で変更したファイル」一覧と取り消し
- プロジェクトからのエージェント実行

確かめ方: プロジェクトを作る → 作業フォルダを設定 → 目的を書いて実行 →
承認を求められる → 拒否すると実行されない → 完了後に取り消せる

検証すること:
- [ ] 承認待ちの間、進行表示が「待機中」になる
- [ ] renderer を再読み込みしても実行が続いており、再購読で経過が見える
- [ ] 実行中に別の会話を開いても、実行が止まらない

## テストの方針

`generic/quality.md` に従い、リスクで選ぶ。全部にテストを書かない。

| 対象 | 種別 | 理由 |
|---|---|---|
| パス境界の検査 | 単体（重点） | ここが破れると作業フォルダの外が壊れる |
| 変更記録と `undo` | 単体 + 結合 | 復旧可能性の根拠そのもの |
| SSE の解釈、`tool_calls` の連結 | 単体（記録した実応答を使う） | サーバごとの差異が入る |
| `prompted` モードの解釈 | 単体 | 曖昧な入力を弾くことが要件 |
| 承認モードの表 | 単体 | 表と実装がずれると危険 |
| 設定の検証と移行 | 単体 | 黙って既定へ落とさないこと |
| Chat の送受信 | 結合（モックサーバ） | — |
| 実サーバとの疎通 | 手動（各段階の確かめ方） | 自動化の費用が見合わない |
| 画面の見た目・操作感 | 手動 | 同上 |

モックのLLMサーバを `packages/core/test/fake-server.ts` として持つ。
SSEの断片、ツール呼び出し、途中切断、非互換応答を再現できるようにする。
