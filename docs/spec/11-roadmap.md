# 11 — 実装順序と検証計画

## 原則

不確実性の高いところから潰す。各段階の終わりに、**オーナーが自分で確かめられる操作**が
1つ増えている状態にする。「基盤だけできたが何も動かない」段階を作らない。

## 順序の考え方

当初はデスクトップのChatを先に作る予定だったが、**エージェント先行**に変えた。

理由: この製品の価値は「LLMに手を動かさせる」ところにあり、
外部のマルチエージェントツールから使えるようになるのが最短の実用化だから。
デスクトップの画面は、動く中身ができてから被せるほうが手戻りが少ない。

```
P0 接続             [完了・実機未確認]
P1 エージェント中核  [中核は完了 / 会話の保存が残り]
P2 文脈の圧縮と recall ← 今ここ。文脈長の小さいモデルではこれが無いと作業が完了しない
P3 ハーネスAPI       ← 外部ツールから使えるようになる
P4 MCP
P5 記憶（ベクトル索引）
P6 Web
P7 デスクトップ Chat
P8 Work と Code の画面
P9 仕上げと配布
```

## P1 — エージェント中核 + 保存 + CLI【中核は完了。会話の保存は未着手】

最も事故が起きやすい部分。**CLIで先に作る**。画面より検証が速く、境界の穴が見つけやすい。

作るもの:
- `store`: 会話の保存（`04-chat.md` の木構造、`07-data.md` の原子的書き込み）

- 変更記録とバックアップ、`undo`
- CLI の `run` / `diff` / `undo` / `runs` / `--json`

確かめ方:
```sh
cd /tmp/sandbox && akari "hello.txt に挨拶を書いて"
akari diff        # → 差分が出る
akari undo        # → 元に戻る
```

検証すること（**ここは重点的にテストを書く**）:
- [x] `../` を含むパス、絶対パス、シンボリックリンク経由で workspace の外へ出られない

- [x] `/work` と `/workspace` を取り違えない（区切り境界での比較）
- [x] 広すぎる場所（`/`・ホーム・Akari のデータ）は作業フォルダにできない
- [x] `.git/` の中は書き換えられない。`.env` `id_rsa` 等は読めない
- [x] `edit_file` で `oldText` が複数一致したら実行されない
- [x] `deniedCommands` が `full` モードでも効き、承認画面を出さずに拒否する
- [x] 作業フォルダの外への操作は、**承認画面を出さずに**拒否する
- [x] コマンドが子プロセスを作った場合、タイムアウトでプロセスグループごと消える
- [x] 実行後に手でファイルを変えた状態で `undo` すると、そのファイルは飛ばされ報告される
- [x] 同じファイルを複数回変えても、実行前の状態まで戻る
- [x] 非対話（パイプ）で承認が要る操作が自動拒否され、終了コード 3 になる
- [x] 同じツール・同じ引数を3回繰り返したら停止する
- [ ] 中断したとき、実行中のコマンドが残らない（実装済み。自動テストは未作成）
- [x] ツール非対応モデルで、代替方式（prompted）に自動で切り替わり、実際にツールが動く
- [x] 代替方式でも、承認とパス境界が同じように効く

- [x] 思考タグの切り出しが、通常の応答のストリームを塊にしない

## P2 — 文脈の圧縮と recall

`16-context.md`。**4B級のモデルでは、これが無いと作業が途中で終わる。**
`read_file` を数回した時点で文脈が尽き、そこから先へ進めない。

作るもの:
- `core/context`: トークン見積り（`usage.prompt_tokens` 優先、無ければ概算）、
  ターン単位の切り分け、閾値の判定
- 圧縮: 5分類（決定 / 確認済み / 棄却案 / 未解決 / 次の行動）の Digest を作る。
  前回の Digest を入力に含めて積み増す。失敗したら機械的な要約へ落ちる
- `recall_search` / `recall_read` ツール
- CLI の `akari recall` / `akari digest`
- 会話への保存（`compactions`）。**生のメッセージは消さない**

前提: P1 の残り（会話の保存 `store`）。生の記録が残っていないと recall が成立しない。

確かめ方:
```sh
akari run "大きめのファイルを何度も読ませる作業"   # 途中で圧縮が起きる
akari digest                                      # 5分類が読める
akari recall "何を棄却したか"                      # 生の記録から引ける
```

検証すること:
- [ ] 圧縮してもターンの境界が壊れず、`tool_calls` と `tool` の対応が保たれる
      （壊れると 400 になる。ここが一番落ちやすい）
- [ ] 圧縮しても生のメッセージが会話ファイルから消えない
- [ ] 圧縮が起きたことが画面とイベントに出る。黙って落とさない
- [ ] Digest が読めない形式で返ったとき、1度やり直させ、それでも駄目なら
      機械的な要約へ落ち、そうと表示される
- [ ] 圧縮された範囲を `recall_search` → `recall_read` で取り出せる
- [ ] `sources` の未知IDを、参照できるように見せない
- [ ] 圧縮しても入りきらないとき、黙って古いメッセージを落とさない
- [ ] **4B級のモデルが5分類を安定して出せるか**（実機。駄目なら分類を減らす）
- [ ] `chars / 2.2` の概算が実際とどれだけずれるか（実測して係数を決める）
- [ ] 圧縮1回にかかる時間（体感が悪ければ先回りして作る方式を検討）

## P3 — ハーネスAPI

外部のマルチエージェントツールから使えるようにする。`12-harness-api.md`。

作るもの:
- `apps/server`: HTTP + SSE、トークン認証、実行の管理と待機列
- イベントの連番と再送（`Last-Event-ID` / `?from=`）
- 承認・停止・取り消し・差分・transcript
- ラベルと `idempotencyKey`
- git worktree による隔離
- CLI の `akari serve`

確かめ方:
```sh
akari serve --print-token
curl -H "Authorization: Bearer $TOKEN" -X POST localhost:7801/v1/runs \
  -d '{"prompt":"READMEを直して","workspace":"/tmp/repo","git":{"worktree":true}}'
curl -N -H "Authorization: Bearer $TOKEN" localhost:7801/v1/runs/$ID/events
```

検証すること:
- [ ] トークンなし・誤トークンは 401
- [ ] `0.0.0.0` へは bind できない
- [ ] `Origin` 付きのリクエストは、トークンが正しくても既定で拒否される
- [ ] SSE を途中で切って `?from=` で繋ぎ直すと、取りこぼしなく続きが読める
- [ ] 保持を超えて取りこぼした場合、`gap` イベントで正直に伝える
- [ ] 同じ `idempotencyKey` で2回叩いても実行が1つしか作られない
- [ ] 2つの実行を別々の worktree で同時に走らせ、互いのファイルを踏まない
- [ ] `transcript` が Discord の2000字で割れ、コードブロックを壊さない
- [ ] 承認要求がHTTPに出て、HTTPで許可・拒否ができる
- [ ] サーバを落としても、走っていた実行の変更記録が残る

## テストの方針

`generic/quality.md` に従い、リスクで選ぶ。全部にテストを書かない。

| 対象 | 種別 | 理由 |
|---|---|---|
| パス境界の検査 | 単体（重点） | ここが破れると作業フォルダの外が壊れる |
| SSRF の検査 | 単体（重点） | ここが破れると内部ネットワークが読まれる |
| ハーネスAPIの認証とCORS | 結合（重点） | ここが破れると外からコマンドを実行される |
| 変更記録と `undo` | 単体 + 結合 | 復旧可能性の根拠そのもの |
| SSE の解釈、`tool_calls` の連結 | 単体（記録した実応答を使う） | サーバごとの差異が入る |
| イベントの再送と `gap` | 結合 | チャットボットが落ちても経過を失わないこと |
| `prompted` モードの解釈 | 単体 | 曖昧な入力を弾くことが要件 |
| 承認モードの表 | 単体 | 表と実装がずれると危険 |
| 設定の検証と移行 | 単体 | 黙って既定へ落とさないこと |
| ターン境界を壊さない圧縮 | 単体（重点） | 壊すと API が 400 を返し、実行が止まる |
| 圧縮しても生が消えないこと | 結合 | 「消さない」がこの機能の前提 |
| 埋め込みの次元・モデル不一致 | 単体 | 混ぜると無意味な結果が出る |
| 索引の検索速度 | 実測 | 方針の前提そのもの |
| Chat の送受信 | 結合（モックサーバ） | — |
| 実サーバとの疎通 | 手動（各段階の確かめ方） | 自動化の費用が見合わない |
| 画面の見た目・操作感 | 手動 | 同上 |

模擬サーバ `tools/mock-llm-server.mjs` に、埋め込みとツール呼び出しの応答を足していく。
