# 16 — 文脈の管理と圧縮

## なぜ要るか

文脈長の小さいモデルでコードを書かせると、数ステップで入りきらなくなる。
そのとき「古い方から黙って捨てる」と、**何を決めたか・何を試して駄目だったかを忘れ**、
同じ失敗を繰り返す。捨てた事実に気づく手段も無い。

そこで、超過した分を**構造化して圧縮**し、以降はその圧縮版を文脈に載せる。
生の記録は捨てずに残し、必要になったら検索して取り出せるようにする。

### 何が文脈を食うのか

思考出力（reasoning）だけではない。実測される順に:

1. **ツールの出力** — `read_file` 1回で数千トークン。最大の要因。
2. **思考出力** — 推論するモデルでは1ステップあたり数百〜数千トークン。
3. 本文とツール呼び出しの引数。

したがって圧縮の対象は**会話全体**であり、reasoning はその一部として扱う。
reasoning だけを圧縮しても、ファイルを数回読めば同じ状況になる。

## 原則

- `MUST` **生の記録は消さない。** 圧縮は「次に何を送るか」を変えるだけで、
  保存されているものを変えない。
- `MUST` 圧縮したことを利用者に見せる。何ステップ分が圧縮され、
  どれだけ小さくなったかを出す。黙って情報を落とさない。
- `MUST` 圧縮結果の各項目に、根拠になった生のメッセージIDを持たせる。
  「なぜそう書いてあるのか」を必ず追える状態にする。
- `MUST` 圧縮に失敗したら、**成功したふりをしない**。決められた退避方法へ落ち、
  そのことを表示する。
- `SHOULD` 直近のやり取りは生のまま残す。直前の文脈が要約になっていると、
  モデルは細部を取り違える。

## いつ圧縮するか

```
[system] [最初の目的] [圧縮版] [直近 N ターンの生] [今回の入力]
                       ↑ ここへ古い分がまとまる
```

判定は各ステップの**モデル呼び出しの前**に行う。

| 設定 | 既定 | 意味 |
|---|---|---|
| `context.windowTokens` | `null` | モデルの文脈長。`null` なら下の絶対値で判断する |
| `context.compactAtRatio` | `0.7` | 文脈長の何割を超えたら圧縮するか（`windowTokens` が分かるとき） |
| `context.compactAtTokens` | `12000` | 文脈長が分からないときの絶対値 |
| `context.keepRecentTurns` | `3` | 生のまま残す直近のターン数 |
| `context.mode` | `auto` | `auto` / `off`。`off` なら圧縮せず、入りきらなければ止める |

`windowTokens` は接続先ではなく**モデルごと**に持つ（`capabilities.byModel[model].contextTokens`）。

取得の順序:

1. `/models` がフィールドで返していれば、それを使う（`02-provider.md`）。
   vLLM は `max_model_len` を返す。
2. 返さないサーバでは、利用者が設定する。
   `akari config endpoints probe -m <モデル> --context <数値>`
3. どちらも無ければ**不明**として扱い、`compactAtTokens` の絶対値で判断する。
   分からないものを分かったふりにしない。

### トークン数の見積り

- **直前の応答の `usage.prompt_tokens` を最優先で使う。** これは
  「実際に送った量」の実測値で、推定より正確。
- 返さないサーバでは文字数からの概算（`chars / 2.2`）を使う。
  概算であることを、表示でも判断ログでも明示する。
- 概算しか無い場合、閾値は**低めに倒す**（既定の `compactAtRatio` を 0.6 として扱う）。
  外して溢れるより、早めに圧縮するほうが被害が小さい。

## 何を圧縮の単位にするか

メッセージ単位ではなく**ターン単位**で切る。

> **ターン** = 1回のモデル応答と、それに続くツール結果の全部。
> `assistant`（`tool_calls` つき）と、対応する `tool` メッセージ群は不可分。

これを守らないと、OpenAI互換APIは
「`tool_calls` に対応する `tool` メッセージが無い」として 400 を返す。
**圧縮はターンの境界でのみ行う。**

圧縮しないもの:

- システムプロンプト
- 会話の最初の利用者メッセージ（目的）。これを失うと何をしていたか分からなくなる
- 直近 `keepRecentTurns` ターン
- 未完了のツール呼び出しを含むターン

## 圧縮の結果（Digest）

```ts
type DigestItem = {
  text: string;
  /** 根拠になった生のメッセージID。ここから原文へ戻れる。 */
  sources: string[];
};

type Digest = {
  /** 決定: こうすると決めたこと。理由も短く含める。 */
  decisions: DigestItem[];
  /** 確認済み: 実際に見て確かめた事実（ファイルの場所、テストの結果、環境の状態）。 */
  confirmed: DigestItem[];
  /** 棄却案: 試したが駄目だったこと。「なぜ駄目か」を必ず書く。 */
  rejected: DigestItem[];
  /** 未解決: まだ分かっていないこと、確かめていないこと。 */
  open: DigestItem[];
  /** 次の行動: このあとやる予定のこと。 */
  next: DigestItem[];
};
```

**棄却案を残すのが要点。** これが無いと、圧縮した直後に同じ方法を試し始める。

```ts
type Compaction = {
  id: string;
  createdAt: string;
  /** 圧縮の対象にしたメッセージID（生は消さない。参照が残る）。 */
  coveredMessageIds: string[];
  coveredTurns: number;
  /** どのモデルで圧縮したか。品質が変わるので記録する。 */
  model: string;
  endpointId: string;
  digest: Digest;
  /** 圧縮前後のトークン数。概算なら estimated: true。 */
  beforeTokens: number;
  afterTokens: number;
  estimated: boolean;
  /** 退避方法へ落ちた場合の理由。 */
  fallback?: 'parse-failed' | 'model-error' | 'aborted';
};
```

会話に `compactions: Compaction[]` として保存する（`07-data.md`）。

## 圧縮のやり方

1. 対象ターンを選ぶ（古い方から、閾値を下回るまで）。
2. **前回の Digest があれば、それを入力に含める。** 毎回ゼロから作り直さない。
   作り直すと、要約の要約になって内容が薄れていく。
3. 圧縮用の呼び出しを1回行う。指示は固定文で、出力は次の形だけを求める。

   ````
   ```akari-digest
   {"decisions":[{"text":"…","sources":["01J…"]}], "confirmed":[…], "rejected":[…], "open":[…], "next":[…]}
   ```
   ````

4. 厳格に解釈する。読めなければ**1度だけ**「形式が違う」と伝えてやり直させる。
   それでも駄目なら退避方法へ。推測で補正しない。
5. `sources` に未知のIDが入っていたら、その項目は捨てずに残すが `sources` は空にする。
   参照できないことを、参照できるように見せない。

圧縮に使うモデルは、既定では**実行に使っているモデルと同じ**。
`context.digestModel` で別のモデルを指定できる（小さいモデルで作業し、
圧縮だけ賢いモデルに任せる構成のため）。

### 退避方法（モデルに頼らない圧縮）

モデルが失敗したときに、黙って古い分を捨てない。次の**機械的な要約**へ落ちる。

- 実行したツールの一覧（名前と主な引数、成否）
- 読んだファイル、書き換えたファイルの一覧
- コマンドの終了コード
- 各ターンの本文の先頭200文字

`decisions` などの分類はできないので、`confirmed` に事実として並べる。
これは劣った圧縮であり、そう明記する（`fallback` を残し、画面にも出す）。

### それでも入りきらないとき

圧縮しても閾値を超える場合（1つのツール出力が巨大など）:

- `context.mode: "auto"` … 直近ターンの**ツール出力**を先頭・末尾を残して切り詰める。
  切ったことを本文に明記する。それでも駄目なら実行を止め、理由を出す。
- `context.mode: "off"` … 圧縮せず、そのまま止める。

**黙って古いメッセージを落とすことは、どのモードでもしない。**

## 生の記録を引く（recall）

圧縮した後でも、生の記録を取り出せるようにする。
これが無いと、圧縮は「失われた」のと同じになる。

### ツール

| 名前 | 引数 | 危険度 | 返るもの |
|---|---|---|---|
| `recall_search` | `query`, `k?`(既定5), `role?`, `includeReasoning?`(既定 true) | read | 一致したメッセージのID・役割・日時・抜粋 |
| `recall_read` | `messageId` | read | そのメッセージの全文（思考出力を含む） |

- 対象は**その会話の生のメッセージ**。既定では他の会話を見ない。
- `recall_read` の出力は `toolOutputLimitBytes` で切る。
- 圧縮が起きた会話でのみツール一覧に出す。圧縮していないなら出さない
  （使う意味が無いツールを渡さない）。
- システムプロンプトに一行加える:
  > 圧縮された部分の詳細が必要なら `recall_search` で探し、`recall_read` で原文を読む。
  > 圧縮版に無いことを「無かったこと」と決めつけない。

### 検索の実装

v1 は**素朴な部分一致**（大文字小文字を無視、正規表現も可）。
1会話のメッセージ数はたかだか数百なので、線形走査で足りる。

`14-memory.md` のベクトル索引は**使わない**。
会話の索引化は 14 でも対象外にしてある。必要になったら、そのとき決める。
先に索引を作らない。

### CLI

```sh
akari recall "認証まわりで何を決めたか"          # 直近の会話を検索
akari recall --conversation <id> "タイムアウト"
akari recall --read <messageId>                  # 原文を読む
akari digest                                     # 今の圧縮版を見る
akari digest --conversation <id> --json
```

`akari digest` は、いま文脈に載っている圧縮版をそのまま出す。
**モデルが何を前提に動いているかを、利用者が読める形で確認できるようにする。**

## 画面での見せ方

- 会話の中で、圧縮が起きた位置に区切りを出す。
  「ここまでの12ターンを圧縮しました（約8,400 → 約1,200トークン）」
- その区切りを開くと Digest が5分類で読める。各項目から原文へ飛べる。
- 圧縮された範囲の生のメッセージも、畳んだ状態で残す。**消えたように見せない。**
- 退避方法で圧縮された場合は、その旨を目立つ形で出す。

## イベント

`05-agent.md` の `RunEvent` に足す。

```ts
| { type: 'compaction-start'; turns: number; beforeTokens: number; estimated: boolean }
| { type: 'compaction-end'; compactionId: string; afterTokens: number; fallback?: string }
```

ハーネスAPI（`12-harness-api.md`）でもそのまま流れる。
外部のマルチエージェントツールが「いつ圧縮が起きたか」を知れるようにするため。

## 設定のまとめ

| 項目 | 型 / 範囲 | 既定 | 効果 |
|---|---|---|---|
| `context.mode` | `auto` / `off` | `auto` | 圧縮するかどうか |
| `context.compactAtRatio` | 0.3〜0.95 | `0.7` | 文脈長の何割で圧縮するか |
| `context.compactAtTokens` | 1000以上 | `12000` | 文脈長が不明なときの絶対値 |
| `context.keepRecentTurns` | 1〜20 | `3` | 生のまま残す直近ターン数 |
| `context.digestModel` | 文字列 / null | `null` | 圧縮に使うモデル。null なら実行と同じ |
| `capabilities.byModel[m].contextTokens` | 整数 / null | `null` | そのモデルの文脈長 |

## 未解決

- 4B級のモデルが、この5分類を安定して出せるか。**未検証。**
  出せない場合は分類を減らす（決定・棄却・次 の3つ）か、
  圧縮だけ別のモデルに任せる構成を既定にする必要がある。
- `chars / 2.2` の概算が日本語混じりのコードでどれだけ外れるか。実測して係数を決める。
- 圧縮の呼び出し自体にかかる時間。ローカルの4Bで数秒かかるなら、
  実行の体感が悪くなる。実測してから、非同期に先回りして作るかを決める。
- 圧縮を挟んだ会話を「続きから」再開したとき、どこまで生を戻すか。
