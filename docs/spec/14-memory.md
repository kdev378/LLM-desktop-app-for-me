# 14 — 記憶（ベクトル索引）

## なぜ要るか

ローカルLLMは文脈長が小さい（4k〜32kが普通）。リポジトリ全部は入らない。
「関係のある部分だけを選んで渡す」仕組みが無いと、そもそもコードを書かせられない。

`grep` で足りる場面も多い。**まず `grep` と `glob` を使わせ、
それで見つからないときの補助**として索引を置く。索引を主役にしない。

## 何を索引にするか

| 対象 | 既定 | 備考 |
|---|---|---|
| 作業フォルダのファイル | 索引にする | `.gitignore` と `.akariignore` を尊重する |
| プロジェクトの資料 | 索引にする | `06-work-and-code.md` の添付 |
| 会話の履歴 | **索引にしない** | v1 では対象外。必要になってから決める |

除外の既定: `node_modules` `.git` `dist` `build` `target` `vendor` `.venv`
`__pycache__` `*.min.js` `*.lock` `*.map`、および 1MB を超えるファイル、バイナリ。

- **対象の一覧は git に聞く**（git のリポジトリなら `git ls-files --cached --others --exclude-standard`）。
  `.gitignore` を自前で解釈すると細かい規則で食い違うため。git でないフォルダは、上の除外と `.akariignore` で決める。
- **秘密のファイル（`.env` など）と秘密の場所は、索引に入れない**（`05-agent.md`）。入れると、検索結果として
  中身がモデルへ渡り、秘密の守りの抜け道になる。`agent.sandbox.allowWorkspaceSecrets` が true でも入れない
  （索引は残り続けるため）。
- worktree（ハーネスAPIの実行ごとの作業用コピー）では、元のフォルダの索引を読むだけにする。
  その実行の変更は入っていないが、候補は `read_file` で確かめるので実害は小さい。

## 保存の形

`07-data.md` の「DBを使わない」方針をここでも保つ。
ベクトルは**フラットなバイナリ1ファイル**に置き、検索は総当たりで回す。

```
<root>/index/<indexId>/          # indexId は作業フォルダの実体のパスの sha256 の先頭16桁
  current.json     # 今使う版（{"generation": "g-…"}）。これの書き換えで差し替える
  g-<id>/          # 版。更新のたびに新しい版を丸ごと書く
    meta.json      # 索引の素性。これが合わないものは混ぜない
    chunks.jsonl   # 1行1チャンクのメタ情報（本文込み）
    vectors.bin    # Float32（リトルエンディアン）。chunks.jsonl と同じ順に dims 個ずつ
  update.lock      # 更新中の目印（更新は同時に1つだけ）
```

- 索引は作り直せる複製（キャッシュ）として扱う。壊れても消えても、会話やファイルは失われない

```jsonc
// meta.json
{
  "schemaVersion": 1,
  "indexId": "01J…",
  "root": "/home/me/proj",
  "embedding": {
    // 索引を作った埋め込み（EmbeddingIdentity）。合わなければ検索しない
    "source": "builtin",
    "model": "<内蔵のモデルID>",
    "revision": "<版>",
    "fileSha256": "sha256:…",
    "contract": "<使い方の約束の版>",
    "dims": 384,
    "maxTokens": 8192,
    "normalized": true
  },
  "chunking": { "maxChars": 1200, "overlapChars": 200, "strategy": "lines-v1" },
  "files": { "src/main.ts": { "hash": "sha256:…", "size": 1234, "mtimeMs": 0, "first": 0, "count": 3 } },
  "counts": { "files": 412, "chunks": 5310 },
  "builtAt": "…", "updatedAt": "…"
}
```

### なぜベクトルDBを使わないか

| 案 | 却下の理由 |
|---|---|
| SQLite + sqlite-vec | ネイティブモジュール。Electron と Node で別ビルド × 3OS。個人用ツールに見合わない |
| hnswlib / faiss | 同上。近似検索が要る規模ではない |
| 外部のベクトルDBサーバ | 常駐が増える。ローカル完結の利点を失う |

**総当たりで足りる根拠（実測、2026-10-29）**: 384次元で **5,000チャンク 2.9ms、50,000チャンク 38.6ms**（1回の検索。
開発用のクラウドの環境の CPU。自動テスト `memory.test.ts` が毎回測って出す）。見直しの目安の 300ms を大きく下回る。

**破綻する条件**: チャンクが20万を超える、または検索が300msを超える。
そのときは近似検索へ移す。それまで作らない。

## 埋め込み

文章を数値の並び（ベクトル）に変える。会話のモデルとは別の、埋め込み専用のモデルを使う。

### 2つの出どころ（2026-10-29 オーナー承認）

| 出どころ | 何か | 既定 |
|---|---|---|
| **内蔵**（`builtin`） | Akari が CPU で動かす小さな埋め込みモデル。**版を Akari の版ごとに固定**する | 標準 |
| **外部**（`endpoint`） | LM Studio / Ollama / 別のマシンなど、OpenAI 互換の `POST {baseUrl}/embeddings` | 設定で選ぶ |

- 内蔵を標準にするのは、どの環境でも同じモデルになり、結果がそろうため。設定なしで使える。
- 外部を選べるのは、1台に集めて VM・コンテナごとのメモリを食わないため、GPU を使うため。
- **内蔵と外部、外部どうしは混ぜない**。同じ名前のモデルでも、動かし方や量子化が違えばベクトルがずれる。
  索引は「どれで作ったか」（下の「同じとみなす条件」）を持ち、違えば検索せずに作り直しを促す。

### 埋め込みの口（`Embedder`）

索引づくり・検索は、この口しか知らない。出どころ（内蔵・外部・将来の段階2）はこの裏で差し替える。

```ts
interface Embedder {
  /** 何者か。索引に記録し、検索のたびに照合する。 */
  identity(): Promise<EmbeddingIdentity>;
  /** kind で文の前に付ける印を変えるモデルがある（検索の問い / 索引の本文）。 */
  embed(texts: string[], kind: 'query' | 'passage', signal?: AbortSignal): Promise<Float32Array[]>;
}

type EmbeddingIdentity = {
  source: 'builtin' | 'endpoint';      // 将来 'lan' を足す（段階2）。足しても他は変わらない
  model: string;                       // 例: 内蔵なら Akari が決めた ID、外部ならサーバのモデル名
  revision: string | null;             // 内蔵: モデルの版。外部: 分からなければ null
  fileSha256: string | null;           // 内蔵: モデルの重みの指紋。外部: null
  contract: string;                    // 使い方の約束（印・プーリング・正規化）の版。例 "e5-prefix-v1"
  dims: number | null;                 // 外部の接続先は、最初に埋め込むまで分からない（null）
  maxTokens: number | null;            // チャンクの大きさをこれに合わせる。外部の接続先は分からない（null）
  endpointId?: string;                 // 外部のとき
};
```

- 取得したベクトルは L2 正規化して保存する。検索は内積（= コサイン類似度）で済む。
- 外部の接続先が埋め込みに対応していない（404 / 400）ときは、索引の機能を使えないと示す。「使えるふりをしない」。
- 外部へは既定16件ずつ送る。413 や 400 が返ったら、半分にして1度だけ再試行する。

### 同じとみなす条件

エンジン（モデルを動かす部品）の小さな違いや脆弱性の修正では、結果は実質変わらない。
だから版の名前ではなく、**名前と実物の両方**で確かめる。

1. **名前**: `model` `revision` `fileSha256` `contract` `dims` が一致する
2. **実物（見本の照合）**: 内蔵のモデルには「決まった文と、その答えのベクトル」を同梱する。
   埋め込みの係につながるたびに見本を埋め込ませ、答えとの類似度が **0.999 以上**であることを確かめる。
   外れたら、その係は使わず、理由を出す（エンジンの更新で本当に結果が変わった場合をここで捕まえる）

外部の接続先には見本が無い。外部の索引は `endpointId` と `model` が一致すれば同じとみなし、
接続先がモデルを差し替えた場合は検出できないことを `akari index status` に書く。

### 内蔵のモデルの置き場（初回に取得）

- 重みはリポジトリに入れない（git clone と更新が重くなるため）。**初回に一度だけ取得**する。
  取得先・版・指紋（sha256）・見本・ライセンスは、Akari の版ごとに固定した一覧（マニフェスト）で持つ。
- 取得したら指紋を確かめ、合わなければ使わずに消す。置き場は `<root>/models/<モデルID>@<版>/`。
- ネットに出られない環境では、同じファイルを手で置けば使える（指紋が合えばよい）。
- 外部の接続先を選んでいるときは取得しない。
- デスクトップ版（P9）のインストーラーには最初から入れてよい（ライセンスが再配布を許すこと。下の「モデルの選び方」）。

### 埋め込みの係（段階1: 同じ PC の中で共有する）

内蔵のモデルは、会話のプロセスではなく、**専用の裏方のプロセス（埋め込みの係）**で動かす。

```
 Akari（対話画面）  Akari（run）  Akari（mcp serve / serve）
        └──────────────┬──────────────┘
                       ▼  この PC の中だけの口（OpenAI 互換の /embeddings）
                 埋め込みの係（モデル1つ）
```

- 最初に埋め込みが要った Akari が係を起こす。データの置き場の**目印（ロック）**で、係は1つだけにする。
- 係は使われない時間が**10分**続いたら、自分で終わる（モデルを手放してメモリを空ける。次は読み込みで数秒待つ）。
- 係が落ちていたら、次に要った Akari が起こし直す。
- 口はこの PC の中だけ（Unix ドメインソケット / Windows の名前付きパイプ、または 127.0.0.1 とトークン）。ネットワークへは出ない。
- 話し方は OpenAI 互換の `/embeddings` に、自分が何者かを返す口（`/akari/embedding-identity`）を足したもの。
  係から見た Akari は「ただの接続先の1つ」になり、段階2でも話し方は変わらない。
- 1回で終わる `akari run` を係にしないため、係は会話のプロセスと分ける。
- モデルを動かす部品（ONNX の実行環境など）は**係の中だけ**で使う。OS ごとの部品が要るものでも、影響が係に閉じる。

### 段階2: 別の VM・コンテナ・PC と共有する（将来。今は作らない）

段階1の係を、ネットワーク越しにも使えるようにする。**今は作らない**（2026-10-29 オーナー承認）。
作るときの要件だけ書いておく。段階1の作りは、ここで書き直さずに済むようにする（下の「拡張の隙間」）。

- **見つけ方**: 標準の仕組み（mDNS / DNS-SD）で `_akari-embed._tcp.local` を名乗る係を探す。DNS の設定は要らない。
  ただし VM の NAT や Docker の標準のネットワークでは届かないことが多い（未確認）。だから**係のアドレスを手で書く方法**を
  確実な道として必ず用意し、探すのは手間を省くおまけとする。
- **残る係の決め方**: 各係が起動時刻と ID を名乗り、いちばん古いものが残る。ほかは退いて、その係を使う。
  時計のずれで2つ残っても、結果は同じ（上の「同じとみなす条件」）なので壊れない。メモリを余分に使うだけ。
- **安全（必須）**: ネットワーク上の係には、コードや文書の本文が送られる。
  - 最初の1回だけ**合言葉（ペアリングの鍵）**を写す。知らない相手は係として使わず、相手からの頼みも受けない
  - **暗号化**する。ペアリングのときに係の証明書の指紋を覚え、以後その相手とだけ話す
  - 既定は無効。有効にした環境だけが探し、名乗る
- 外部の接続先（LM Studio など）を使っている環境は、段階2に加わらない。

### 拡張の隙間（段階2・OAuth などを後から足すために、今の作りで守ること）

- 索引づくり・検索は `Embedder` の口だけを使う。出どころの種類で分岐しない
- `EmbeddingIdentity.source` は種類で分ける形にする（`lan` を足しても、ほかの項目と索引の形は変わらない）
- 係との話し方は、PC の中でもネットワーク越しでも同じ（OpenAI 互換＋何者かを返す口）。違うのは口の開き方と認証だけ
- 係を探す処理は「係の居場所を返す」1か所にまとめる（段階1はロックとソケット、段階2は探索と手書きのアドレスを足す）
- 係への認証は差し込める形にする（段階1はトークン、段階2はペアリングと証明書の指紋）

### モデルの選び方（未決。実測してから決める）

内蔵の標準にするモデルは**まだ決めない**。条件:

| 条件 | 理由 |
|---|---|
| ライセンスが再配布を許す（MIT / Apache 2.0 など） | 同梱・取得の配布をするため。非商用（CC BY-NC）は外す |
| CPU で軽い（エンコーダ型で、実際の計算量が小さい） | 係のメモリ・索引づくりの時間 |
| 日本語・英語・コードが混ざっても当たる | オーナーの資料は日本語、対象はコード |
| 1回に読める長さが十分（目安 2,000 トークン以上） | チャンクを切り詰めずに入れるため |
| 取得するファイルが小さい（目安 150MB 以下） | 初回の取得 |
| 公開元が版を固定して出している | 版を固定する前提 |

候補と、確かめたこと（2026-10-29。公開元の数値は公開元の測定であり、こちらでは測っていない）:

| 候補 | 確かめたこと | 気になる点 |
|---|---|---|
| `ibm-granite/granite-embedding-97m-multilingual-r2` | 97M（実効 約28M）、384次元、8,192〜32,768トークン（資料で食い違う）、200言語以上、ModernBERT、Apache 2.0、ONNX あり（2026-05 公開） | 公開元の順位以外の独立した評価は未確認 |
| `hotchpotch/bekko-embedding-v1-a25m` / `-a8m` | 実効 約25M / 約8M、384次元（256/128/64 に縮められる）、8,192トークン、MIT、Transformers.js で動く見本あり | 数値は作者の表のみ。個人の公開で、保守の続き方が読めない |
| `codefuse-ai/F2LLM-v2-80M`（2026-10-29 追加） | 80M（実効 約32M）、320次元、Apache 2.0。コード検索が強い（MTEB Code 68.0） | 日本語の点が表に無い。生成用の型のモデルなので、問いに付ける指示の書き方で結果が変わりうる |
| `cl-nagoya/ruri-v3-30m` / `-70m` | 37M（実効 約10M）・256次元、8,192トークン、JMTEB 平均 74.51（30m）、70m は Apache 2.0 | 日本語向け。英語・コードの強さは未確認。30m のライセンスは本体の説明で未確認 |
| `minishlab/potion-multilingual-128M`（静的） | 256次元、MIT、bge-m3 から蒸留、101言語。表を引くだけで非常に速い | 精度は一段落ちる。最軽量の比較の基準として測る |
| `intfloat/multilingual-e5-small` | 118M、384次元、MIT | **512トークンまで**。日本語のチャンクが入りきらない。旧来の基準として測るだけ |

`harrier-oss-v1-270m`（デコーダ型 270M・640次元で重め。高精度の外部用の候補にはなる）、
EmbeddingGemma 2（約740M の多モーダル。「270M のテキスト構成」は確認できなかった）。

**暫定の第一候補: `granite-embedding-97m-multilingual-r2`**（2026-10-29 オーナー）。実測で問題が出たら見直す。
確かめること: Node で動くか（ModernBERT を Transformers.js / ONNX の実行環境が扱えるか）、日本語のトークンの効率、CPU での速さ。

**自作のモデルも同じ枠で扱う**。既存のモデルを手元の資料で追加学習したもの・軽い静的モデルへ蒸留したものなども、
ONNX などで書き出してマニフェスト（取得先・版・指紋・見本・ライセンス）に載せれば、内蔵のモデルとして差し替えられる。
比べるときは同じ測り方を使う。元のモデルのライセンス（Granite なら Apache 2.0）を引き継ぐ。

**測り方**（道具: `tools/embed-bench/`、オーナーの手元で動かす）: このリポジトリ自体（日本語の仕様書と TypeScript のコード）を対象に、問いと正解の箇所の組を数十作り、
当たり方・索引づくりの時間（CPU）・係のメモリ・ファイルの大きさを表にする。結果を見て、オーナーが決める。
エンジン（OS ごとの部品が要る実行環境か、WebAssembly か）もこのとき決める。

## チャンクの切り方（`lines-v1`）

v1 は素朴に行単位で切る。言語ごとの構文解析はしない。

- 最大 1200 文字、前後 200 文字の重なり。ただし**モデルが1回に読める長さ（`maxTokens`）を超えない**ように縮める
  （日本語は1文字あたりのトークンが多い。超えた分は黙って切られ、索引に入らないため）。
- 行の途中では切らない。
- 各チャンクに `{ path, startLine, endLine, text }` を持たせる。
  **検索結果は必ずファイル名と行番号を返す**。モデルがそのまま `read_file` で確かめられるように。
- チャンクの先頭に `// path/to/file.ts:120-160` の1行を付けて埋め込む。
  ファイル名自体が手がかりになるため。

将来コード対応の切り方（関数単位）に変えるときは `strategy` を上げ、
古い索引は作り直す。混ぜない。

## 更新

- **実行の最初に、変わったファイルだけ自動で更新する**（2026-10-29 オーナー承認）。
  まず大きさと更新時刻で候補を絞り、指紋（SHA256）で確かめる。
  変わったファイルが多いとき（既定50件超）は自動では更新せず、`akari index update` を促す。
  検索で当たったファイルが索引の後で変わっていたら、結果に「索引の後で変わっています」と添える。
- ファイル単位の SHA256 で変更を検出する。変わったファイルのチャンクだけ作り直す。
- 消えたファイルのチャンクは削除する。
- `vectors.bin` の削除は「詰め直し」で行う。穴を残さない。
  詰め直しは新しいファイルへ書いて `rename` する（`07-data.md` の原子的書き込み）。
- 更新は同時に1つだけ（索引ごとの目印のファイル）。検索は更新中でも、差し替える前の索引を読む。
- 更新は中断されうる。**新しい版を全部書いてから `current.json` を差し替える**ので、途中で止まっても
  前の版がそのまま使える（半端な索引で検索しない）。止まった版の残りは次の更新で片付ける。
  `akari index status` に「前回の更新は途中で止まりました」と出る。
  （2026-10-29 変更。当初の「`dirty` を立てて、立っていたら使わない」より、止まった後も検索が使える）
- `meta.json` か中身が読めない・数が合わない索引は「壊れている」として使わず、作り直しを促す。

## 検索

```ts
memory_search(query: string, k?: number, path?: string): SearchHit[]
type SearchHit = { path: string; startLine: number; endLine: number; score: number; text: string };
```

- 既定 `k = 8`。上限 30。
- `path` を渡すとその配下だけに絞る。
- **スコアをそのまま見せる**。閾値で黙って捨てない。関連が薄いことは数字で分かるようにする。
- 結果の合計文字数は `toolOutputLimitBytes` で切る。
- 索引が無い / 壊れている / 埋め込みモデルが違う → 検索せずに理由を返す。
  **別のモデルのベクトルと混ぜて検索することは、絶対にしない**（無意味な結果が出るため）。

- **使えるときだけ渡す**。索引が無い・壊れている・モデルが違う・係につながらないときは `memory_search` を渡さない
  （使えない道具でモデルを迷わせない）。対話画面・`run`・ハーネスAPI・`mcp serve`（読み取りの道具として）で同じ扱い。

### ツールとしての位置づけ

システムプロンプトにこう書く。

> ファイルの場所が分かっているなら `read_file`、名前で探せるなら `glob` か `grep` を使う。
> `memory_search` は「どこにあるか分からない」ときの補助。返るのは候補であって答えではない。
> 必ず `read_file` で現物を確かめてから編集する。

## CLI

```sh
akari index build              # 作業フォルダの索引を作る
akari index update             # 変わったファイルだけ
akari index status             # 件数、モデル、最終更新、索引の後で変わったファイル、今の設定で使えるか
akari index search "認証はどこ" -k 5
akari index rm
```

`build` は進行を出す（何ファイル中何ファイル、経過時間）。
埋め込みはローカルLLMでも時間がかかるので、無反応にしない。

## 設定

| 項目 | 既定 | 効果 |
|---|---|---|
| `memory.enabled` | `true` | 索引があれば使う。false なら、索引があっても使わない（索引は `akari index build` で作るまで無いので、既定で何かが送られることはない） |
| `memory.embedding.source` | `"builtin"` | `builtin`（内蔵）/ `endpoint`（外部）。将来 `lan` を足す |
| `memory.embedding.endpointId` | `null` | 外部のとき。未指定なら生成と同じ接続先 |
| `memory.embedding.model` | `null` | 外部のときのモデル名。未指定なら索引を作れない（推測しない。候補は一覧から示す） |
| `memory.helperIdleMs` | `600000` | 埋め込みの係が、使われずにこの時間たったら終わる |
| `memory.autoUpdateMaxFiles` | `50` | 実行の最初に自動で更新する、変わったファイルの上限 |
| `memory.maxFileBytes` | `1048576` | これを超えるファイルは索引にしない |
| `memory.chunkChars` | `1200` | チャンクの最大文字数（モデルの上限で縮むことがある） |
| `memory.overlapChars` | `200` | 重なり |
| `memory.batchSize` | `16` | 1回に埋め込む件数 |
| `memory.topK` | `8` | `memory_search` の既定 |

内蔵のモデルの ID と版は設定に出さない（Akari の版で固定する。環境ごとにばらつかせないため）。

## プライバシー

- **接続先が外部の場合、索引を作るとリポジトリ全体が外部へ送られる**。
  索引の作成前に、対象ファイル数と合計サイズを示して1度確認する。
- ローカルの接続先ではこの確認を出さない（毎回聞かない）。
- 索引の中身（`chunks.jsonl`）には本文がそのまま入る。
  設定の書き出し（`07-data.md`）には**含めない**。
