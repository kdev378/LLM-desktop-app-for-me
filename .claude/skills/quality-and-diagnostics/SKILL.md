# Quality and Diagnostics

## 入力

期待される挙動と実際の挙動、関連する成果物やログ、環境とバージョン、変更範囲、実行してよい操作の範囲。

## 手順

1. 種別を選ぶ: デバッグ / テスト / コードレビュー / セキュリティ点検、またはその組み合わせ。
2. 範囲とリスクを決める。デバッグなら再現するか証拠を集める。レビューなら差分全体と呼び出し元を見る。
3. 仮説やリスク箇所を、確からしい順に並べる。最も見分けのつく小さな検査で試す。
4. 境界をまたいでエラーを追い、失敗経路とデータ・安全性への影響を調べる。
5. 修正は依頼されたときだけ行う。現実的なら再発防止の検査を足す。
6. 影響する検査をやり直し、合格・不合格・未実施を区別する。

## 判断基準

正しさ、データ喪失、認可、インターフェース互換性、利用者から見える退行を、書き方の好みより優先する。指摘には証拠と影響を付ける。

## 出力

範囲 / 証拠 / 重大度順の指摘 / 原因または残った仮説 / 許可された範囲での変更 / 実行したテストと結果 / 残るリスク。

オーナーはコードから妥当性を判断しないので、各指摘に「放置すると何が起きるか」を一行付ける。

## うまくいかないとき

再現手段、アクセス、ツールがないことを、成功の主張へ変えない。確度と、次に何を確かめれば切り分けられるかを述べる。症状を隠さない。
