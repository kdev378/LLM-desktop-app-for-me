# Architecture and Interface Design

## 入力

目的、利用者、主要な流れ、制約、既存システムの状況、判明している入出力、不確実な点。未指定の好みは未知のままにする。

## 手順

1. 要件、制約、仮定、未知を分ける。
2. 後から変えにくい境界と、データ喪失のリスクを特定する。
3. 主要な入出力、データの形、所有者、エラーの意味、互換性と移行の期待を定義する。
4. 実現可能な案だけを、複雑さ・戻しやすさ・運用・テスト・安全性・変更コストで比較する。
5. 十分な範囲で最も単純な案を選ぶ。先送りする拡張は先送りと明記する。
6. 危ない仮定を早く検証できる実装順序を作る。

## 判断基準

パターン、サービス分割、抽象は、名前が有名だからという理由では採用しない。現在ある制約か、費用の大きくなり得る境界に対応している必要がある。

## 出力

背景の要約 / 要件と未知 / 構成要素の案 / インターフェースとデータの定義 / 主要な判断と代替案 / リスク / 検証計画 / 段階的な実装計画。オーナー向けに、各案が製品の使い勝手・壊れにくさ・後の変更しやすさへどう効くかを平易に併記する。

## うまくいかないとき

欠けている決定が製品を根本から変えるなら、推測で埋めずに「未解決の決定」として切り出して聞く。影響の小さい欠落は、戻せる generic の既定で埋めて記録する。
